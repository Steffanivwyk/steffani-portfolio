Scale Point Marketing · Operating System Case Study

Designing the operating layer behind a growing marketing agency.

I originally joined Scale Point Marketing in a Paid Media and CRM role. As I became more involved across client strategy, reporting, QA and delivery, a larger operational issue became clear. The agency already had capable specialist tools, but information and decisions were distributed across CRM records, ad platforms, meetings, task boards, Slack conversations and individual team members.

The problem was not a lack of software. It was the lack of a connected operating model around the software.

The challenge

Too much critical context lived between systems

Campaign data, lead outcomes, strategy, approvals and delivery activity were all available, but they did not naturally form one operating loop.

The agency needed a consistent way to answer five questions

What is happening?What do CRM, campaign and website signals actually show?
Why is it happening?What does the evidence suggest about the current strategy?
What should change?What decision or experiment should happen next?
Who needs to act?Which person or department owns execution?
Did it work?What happened after the change was implemented?
The problem in practice

A decision could start in one place and finish in five others.

A campaign decision might be made in a meeting, execution discussed in Slack, work tracked somewhere else, campaign data held in Meta, lead outcomes in GoHighLevel, and the original reasoning left in someone's memory.

Meeting→ Slack→ Task board→ Meta→ GHL
The proposal

Build one operating layer around the tools already in use

The original proposal was not to replace specialist systems. It was to connect them, preserve each system's role, and create one repeatable management model around strategy and delivery.

Source systems

Where the work already lived

  • GoHighLevel for CRM and pipeline activity
  • Meta for delivery and paid-media performance
  • Microsoft Clarity for landing-page behaviour
  • Monday for task execution where appropriate
  • Slack for team communication
  • Fathom and strategic documents for context
→
Orchestration

Automation and interpretation

  • n8n reads, moves, aggregates and classifies
  • AI assists with architecture, logic, synthesis and QA
  • Exception handling makes broken data visible
  • Approval gates protect strategic and client-facing decisions
→
Operating layer

Two connected Airtable systems

  • Strategy Command Centre stores strategic memory
  • Tasks & Handoff System stores delivery state
  • Approved actions move between them through controlled bridges
  • Results return to strategy for the next review cycle
The core principle: connect and interpret existing systems rather than creating another platform that duplicates them.
The operating loop

Evidence → judgement → execution → learning

The system was designed so strategy and operations remain linked without becoming the same thing.

GHL / Meta / Clarity / Commercial data → What is happening? → Strategy Command Centre → Why is it happening? → What should we test? → Operations → Results back to Strategy
STRATEGY OWNS WHYStrategic rationale, evidence, hypothesis, decisions, tests and learning.
OPERATIONS OWNS DELIVERYWho, what, when, QA, approvals, handoffs, launch and completion state.

Strategy screenshot 01

Portfolio Priority: strategic attention across the client portfolio

I created a portfolio view that combines review timing with strategic attention. Review RAG shows whether a formal strategy review is due, while Strategy Attention remains a separate judgement about whether an account needs intervention now.

This distinction matters because a client can be fully up to date with its review cadence and still require urgent strategic attention because performance, conversion or another constraint has changed.

What this solved
It created a structured answer to: Which client should I review first?
Portfolio Priority: client-level prioritisation using review cadence, RAG logic and strategy attention.
Strategy screenshot 02

System Guide & Checklists: building the operating logic into the system

A system is difficult to scale if the knowledge required to use it exists only with the person who built it. I created a guide directly inside the Strategy Command Centre covering how the system works, new client setup, formal strategy reviews, testing and implementation, prioritisation and evidence requirements.

Each guide section explains the purpose, when to use it, the process and the checklist required before the work is considered complete.

What this solved
It reduced dependence on undocumented knowledge and made the Strategy Command Centre a repeatable operating framework rather than a personal dashboard.
Embedded process documentation supports onboarding, consistency and repeatability.
Strategy screenshot 03

Client Strategy Workspace: making the current strategy visible and traceable

Instead of storing strategy across meetings, documents and Slack threads, the Client Strategy Workspace brings the current reasoning into one structured view. It captures the reason the strategy exists, recommended actions, active tests, strategy status and review timing.

The important part is the reasoning behind the action. A change to an ad angle, landing page or CRM process can be connected back to the strategic constraint that made the action necessary.

What this solved
It reduced the gap between performance evidence and execution by making the strategic why visible alongside the next action.
Client Strategy Workspace: current strategic rationale, recommended actions, active tests and review cadence.

Operations screenshot 03

QA Needing Action: turning quality control into a structured workflow

Quality control was designed as a process rather than an informal message asking someone to check an asset. The QA system supports stages such as Draft, Submitted, In Review, Returned, Resubmitted, Passed and Blocked.

Maker ownership, reviewer status, client, deliverable and fix notes can stay attached to the same work item.

What this solved
Corrections and rework no longer need to disappear into chat. QA can become measurable operational evidence.
Structured QA with maker ownership, review states and fix-note visibility.
Operations screenshot 04

Performance Alerts & Controls: turning data into operational attention

Performance data is only useful when it helps someone decide what to do. The performance-control layer converts live ad evidence into action states such as Keep Running, Creative Watch, Learning / Needs Data and Allocation Watch.

The design deliberately distinguishes poor performance from insufficient evidence. A new creative with limited spend should not automatically be treated as a failed creative.

What this solved
It reduced the risk of premature creative decisions based on incomplete data.
Performance evidence becomes a visible action state rather than another reporting metric.
Operations screenshot 05

Live Creative Health: monitoring the creative lifecycle

The live creative view connects active ads to learning stage, performance state and required action. Instead of reducing every ad to good or bad, the system recognises stages such as Discovery, Optimisation and Scaling.

What this solved
Creative decisions can reflect maturity and available evidence rather than a single metric viewed without context.
A lifecycle-based creative health view connecting Meta activity to operational action.

Creative Library: connecting assets to delivery state

The visual library connects creative assets to client, launch readiness, planned go-live timing and Meta status. It gives the team an operational view of creative inventory instead of relying on folders alone.

Additional operational controls

Handovers and launch approval

These controls are part of the same Operations system even where the public portfolio does not show every internal screen in full.

Department Handovers

Making cross-functional transitions explicit

Marketing delivery often breaks at the point where one specialist finishes and another needs to begin. The handoff layer records the work package, client, current state, next owner, timing and completion status.

Strategy→Creative→QA→Paid Media

What this solved: transitions no longer need to depend entirely on someone remembering to message the next person.

Approval Hub

Separating finished from ready to launch

A creative can be finished but still not be QA passed, client approved or ready to launch. The Approval Hub keeps those states separate so completion is not confused with permission to go live.

Asset complete→QA→Client approval→Launch ready

What this solved: clearer launch gates and less ambiguity between production completion and campaign readiness.

n8n automation layer

The Airtable interfaces are the visible layer. n8n connects the system behind them.

The automation architecture is organised by business purpose, with each workflow owning a defined responsibility instead of trying to make one giant automation do everything.

Core principle

GHL keeps raw CRM history. Airtable keeps lean strategic evidence.

n8n handles transport, aggregation, classification and controlled writes between those layers. The system avoids copying entire CRM histories into Airtable because doing so would create duplicate data, conflicting sources of truth and unnecessary system weight.

Universal GHL strategy extraction

A reusable worker processes one configured client per execution and reads contacts, opportunities, conversations, appointments and confirmed bookings. It writes strategic summaries and selected exceptions rather than raw CRM rows.

Design governance

Rules that keep the system trustworthy

Automation was designed to improve decision speed without making important actions invisible or uncontrolled.

Preserve the source of truthDo not duplicate entire specialist systems without a strong operational reason.
Read before writeAutomation should understand the current record and system state before creating consequential changes.
Human approval where judgement mattersStrategy, client-facing actions and important operational decisions remain reviewable.
Make failures visibleBroken access or missing data becomes a visible health issue rather than silently producing misleading reporting.
Configuration before duplicationNew clients should be onboarded through configuration wherever possible.
Separate strategy from executionStrategy owns the rationale and learning. Operations owns the delivery state.
Design for repeatabilityProcesses are documented and built to be reused by the wider team.
Use AI as a collaboratorAI accelerates build and analysis, but source systems and human validation remain authoritative.

Implementation journey

From proposal to working system

The case study reflects an iterative build. It does not present the wider future-state proposal as if every component was already live.

01 · Diagnose
Map fragmentation and operational bottlenecks.
Client information, reporting, approvals, handoffs and strategic memory were distributed across multiple tools and people.
02 · Propose
Define the Scale Point Operating System concept.
Keep specialist systems in place, add a connected management layer and introduce AI and automation behind controlled human workflows.
03 · Build Strategy
Create and test the Strategy Command Centre.
Implement lean strategic evidence, client isolation, review logic, source-of-truth rules and recurring strategic memory.
04 · Build Operations
Create a separate delivery and handoff model.
Structure tasks, QA, defects, handovers, creative health, approvals and delivery visibility around ownership and state.
05 · Connect
Build controlled n8n bridges and reusable workers.
Move approved strategy into execution, return delivery status to strategy and reduce client-by-client rebuilding through configuration.
06 · Iterate
Use real client data to identify edge cases.
Correct source mismatches, access failures, stale data, duplicates and reporting assumptions as the system is tested across accounts.

What the system demonstrates

The strongest part of the project is not any individual Airtable view or n8n workflow. It is the operating model behind them: data → evidence → strategic interpretation → human decision → controlled execution → QA → launch → performance → learning → back into strategy.

Marketing operations is not just about automating tasks. It is about creating an environment where the right information reaches the right person, at the right stage, with enough context to make a good decision.
